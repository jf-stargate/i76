# Bootstrap v1.0.3: cold-start agent procedure

This procedure is independent of conversation memory. A new agent needs only the repository URL, GitHub read access, and—if proposing changes—permission to create an isolated branch/PR. No previous chat transcript or local cache may be assumed.

**Trust root:** accepted policy files from the *current default-branch commit*. Read the current SHA before reading policy, then read files at **that explicit SHA** to prevent a mixed-version bootstrap. Never substitute a PR's edited `AGENTS.md` or protocol as authority.

## Startup transaction

1. `DISCOVER`: Resolve `jf-stargate/i76`, default branch and immutable head SHA `B`. If inaccessible, stop publication.
2. `READ`: Fetch `AGENTS.md`, `agent/protocol/VERSION`, `agent/protocol/access.yaml`, and this document at **ref `B`**. Verify version consistency. Unknown major schema: no write permissions.
3. `ASSESS ENFORCEMENT`: Determine branch restrictions, required PR checks, configured formal-review count, and whether current credentials can bypass restrictions. Missing permission to inspect them is **unknown**, not evidence they exist. In unknown/unenforced state, proposals only; do not merge or direct-push.
4. `DISCOVER CONTEXT`: List relevant branch and PR states, accepted `agent/promotions/`, `manual/reference/`, and historical `ref/`. Read [documentation workflow](../../manual/roadmap/DOCUMENTATION_WORKFLOW.md) and [documentation-impact template](templates/DOCUMENTATION_IMPACT.md); find binary/Ghidra baseline digests. Treat `ref/` as a legacy checkpoint, not the target for new canonical findings. If an input is not available, record that gap; do not fabricate an asset path.
5. `PLAN`: Declare `track`, research topic, expected outputs and read/write scope. Work is permitted to overlap other agents. Consult active PRs to avoid unnecessary duplication, not to acquire a global lock.
6. `ALLOCATE`: For persistable work, generate `run_id = <track>-<UTC_YYYYMMDDTHHMMSSZ>-<8 secure random lowercase hex>`. Atomically create branch `agent/<track>/<run_id>` at `B` using a create-only ref operation. If the ref already exists, allocate a new run ID. No shared branch and no force update.
7. `WRITE`: Changes to a run's `agent/runs/<track>/<run_id>/` belong to that one run. Include a `manifest.json`, structured `findings.json` (can be empty), and `validation.json`. Code should be in versioned scripts or referenced with exact Git blob/checksum. For each **new substantive research run**, include a documentation-impact note at `artifacts/DOCUMENTATION_IMPACT.md` (using the linked template), and list its digest/bytes as a normal manifest artifact. A finding may require no canonical update; state that explicitly. The handoff is a procedural expectation rather than a newly enforced CI condition. Do not mix canonical documentation edits into a run-only PR.
8. `PREFLIGHT`: Validate schemas, path scope, prohibited content, artifact SHA-256, original binary/Ghidra identities and the *original* repo base SHA. Inspect concurrent accepted changes and conflicts. An unchanged, green-checked **isolated run-only** PR need not rebase after an unrelated run merges. For canonical documentation, promotions, baselines, shared tools or governance, update against current `main` and obtain fresh trusted validation. Never force overwrite.
9. `PROPOSE`: Open PR; explicitly state whether it adds a run only, modifies shared tooling, or requests authoritative promotion. Research PRs link the documentation-impact handoff; canonical/promotional updates are separate. **Opening a PR does not make its contents authoritative.**
10. `ACCEPT`: With active protection, a run-only PR may be merged by the human maintainer if its **unchanged head** has passed required `integrity`, it remains mergeable, and its findings/scope are reviewed; the original base need not equal the newest `main`. Canonical, promotion, baseline, shared-tool and governance PRs additionally require explicit maintainer acceptance, up-to-date base reconciliation and a fresh trusted check. This extra requirement is **procedural**, not enforced by the global loose GitHub check rule.
11. `RECORD`: A merged run becomes immutable. Link its merge commit, PR, original base commit, findings and validation in subsequent promotions. Do not edit it to correct a conclusion: create another run with `supersedes`/`contradicts` references.
12. `DOCUMENT`: When the maintainer requests a documentation reconciliation or a subsystem milestone is ready, the **designated repository/documentation steward** discovers merged runs (including older runs without a handoff), reconciles competing evidence, and prepares the promotion record and `manual/reference/` edits in a fresh-base documentation PR. The steward does not rewrite `ref/` or merged runs and never self-merges. Documentation generation is not an unattended background service.

## Failure recovery and concurrent work

- **Chat interrupted before branch creation:** no repository state was changed; allocate a new run on restart.
- **Chat interrupted after branch creation:** reopen branch and manifest; the branch/run ID is the durable identity. If abandoned, retain PR/branch history or close PR with a reason; do not turn the directory into a shared scratchpad.
- **Two agents study the same function:** both may publish separate immutable runs. A promotion selects or reconciles their findings; avoid last-writer-wins.
- **Research conversation ends before a documentation handoff:** its merged findings and evidence remain usable; the documentation steward can reconstruct the impact from the accepted run and the legacy reference. Do not mutate the merged run to backfill a handoff.
- **Two agents request the same research milestone (`v21`):** version is assigned **at promotion**, not at run allocation. Only one accepted milestone may claim the slot without explicit version/namespace distinction.
- **`main` advances:** do not rebase isolated run-only PRs solely because unrelated work merged, provided the head is unchanged, checks passed and no conflict exists. Revalidate canonical, governance and shared changes against updated `main`. Never silently adopt another agent's canonical edits.
- **Conflicting `manual/` conclusions:** both findings remain discoverable; canonical reference stays unchanged until reviewer approves a reconciliation PR.
- **No GitHub enforcement visibility:** agent may keep work on an isolated branch/draft PR but must not autonomously merge or report it as accepted.
- **Same GitHub identity used by agent and user:** accepted for this small manually supervised experiment; there is no identity-based independent review, and the agent must not self-merge. The human makes the merge decision. Passing CI alone is never approval.
- **Security or licensing uncertainty:** fail closed on publication of suspicious binaries, secrets or unreviewed proprietary resources.

## First-time protocol deployment

The repository retains historical `ref/`, `scripts/`, and `snapshot/` trees. The publication protocol is accepted; the live ruleset 25664125 and trusted CI must still be checked at each new agent bootstrap. Formal independent GitHub approvals and separate credentials are intentionally not required for this experiment. Protocol 1.0.3 retains `autonomous_run_merge: false`; documentation stewardship adds no merge authority or new GitHub ruleset.

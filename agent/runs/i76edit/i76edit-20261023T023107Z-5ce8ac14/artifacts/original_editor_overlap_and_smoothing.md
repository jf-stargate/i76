## Native dispatch, scan, and write graph

- `0040A6E0` enumerates 80 object-zone buckets in increasing numeric order (`0040AACA`–`0040AAF1`), each following singly forward `node+0` list links (`0040AAB8`–`0040AAC4`); object classes are filtered at `0040A72F`–`0040A754` for 2,3,0x50,0x51,0x52,0x53.
- `00409840` and `0041C430` head-insert new 12-byte nodes. `00409A90` relocates a changed-zone object by unlinking then inserting at the destination head. Thus per-zone age ordering and cross-zone numeric ordering are **distinct** and must not be collapsed into a single global creation-order rule. Loading `00409EB0` uses repeated head insertions, meaning saved list order also matters.
- Reads plane-0 height at object zone-local anchor into `object+0x0C` (`0040A754`–`0040A77D`), then parses eight-character ASCII dimensions `object+0x64/+0x6D`, positive only; rounds up to grid cells of 5, rotates four integer corners through `00412CF0`, and computes integer extrema (`0040A7AC`–`0040A8C9`). Rotation uses signed object angle at `+0x18`, with a `pi/180` constant `00432150` and fpu rounding; the exact transform/rounding has not been dynamically reproduced.
- For already-derived integer extrema (`minX,minY,maxX,maxY`), scan X *outer*, Y *inner*: `minX'-1 ... maxX'` and `minY'+1 ... maxY'+2`, where `minX' = (minX == 0 ? 1 : minX)` and similarly for Y, with widths based on the unadjusted extrema. This is not a polygon footprint and may extend outside its geometric rectangle. Original code iterates with `ebx=-1` (`0040A8DC`) and `ebp=1` (`0040A8F8`). Bounds are neither symmetric nor based on nearest-to-anchor distance.
- The *first* work-plane-1 sample != `0x8000` wins (`0040A95F`–`0040A97A`). If none exists, fall back to `object+0x0C` (the plane-0 anchor sample), promoting zero to one (`0040A992`–`0040A9B5`). A fallback height of `0x8000` is **not** promoted to a valid value. This is important for correctly expressing the protection invariant.
- The routine unconditionally assigns the selected uint16 height to all region samples in the work plane at `0040AA5C`. It then conditionally calls material writer `0041F4A0` at `0040AA73`, selecting surface 6 for classes 0x50/0x51 and 7 for 0x52/0x53. Classes 2/3 write height only. Height precedence and surface-material precedence are therefore independent.
- Because earlier objects can seed plane 1 and later objects can reuse that seed, first-valid-height propagation can cross an **overlap chain** A->B->C where A and C have no common samples. The outcome depends on other preexisting samples and the actual X-major scan priority. This propagation is a derived consequence of the native branches, illustrated by seven *analytical* (not original-code) tests.
- A post-stamp update at `0040AAA4` clears EAX, `0040AAA8` populates AX from a 16-bit work-plane sample, then `0040AAB0` compares EAX with `0xffffffff` before writing `object+0x0C`. That comparison cannot succeed for a zero-extended 16-bit value. Consequently the update is effectively unconditional for eligible objects, including the possible `0x8000` sentinel. This is a static original-instruction fact; visible/editor-run consequences are unmeasured. Final refresh `0040AC20` subsequently obtains height from plane 0 after merge.

## Interaction with road grading

`0040E3C0` invokes object grade, road grade, object grade again, four road-smoothing passes, then merges terrain heights and performs final refresh. Road `00421DF0` has mode-dependent writes: in modes 2 and 4, its cell-write logic first checks whether plane-1 height is `0x8000`, so already stamped object height blocks those particular writes. Neighbor interpolation routine `00421BE0` reads surface through `0041F150` and height through `0041F2B0` (selector 1); for **existing valid heights**, surface values 6 or 7 do not enter its branch requiring `surface < 6` (`00421D40`–`00421D4C`). If the height remains sentinel, however, `00421BE0` enters its other branch and may write a surface or height. Do not generalize that material 6/7 *alone* prevents all road alterations.

## Zone-granular but not globally simultaneous smoothing

`00422870` samples nine heights for center cells of material 2,3,4, writing a 128x128 scratch plane before a `rep movsd` copyback (`00422BDA`–`00422BDF`). `0041F2B0` mode 100 accesses global plane-1 heights and can read across zone boundaries. Scheduler `0040E3C0` calls this zone-local kernel sequentially over the active zone IDs 0..79, then repeats this sweep four times. Therefore the **same pass** in a numerically later zone can read neighboring samples already updated in an earlier zone. Snapshot semantics hold **within a zone**, not across the entire multi-zone terrain. A small averaging example demonstrates differing values between globally synchronous and zone-sequential update schedules; these values are only illustrative and are not exact FPU output measurements from the executable.

## Retail mission audit as counter-evidence to overbroad causality

Historic v20 first-LOD polygon probes include 386 intersection placements / 13,661 points. Existing `v20_intersection_footprint_per_placement.tsv` contains material 6/7 at **381/386** placements, so the mere presence of surface 6/7 is not diagnostic of a large height gap. Among the 19 worst-point cases in `v20_largest_footprint_discrepancies.tsv` (each exceeds 0.25 units), worst-point terrain materials are 11 cells of class 1, four of class 0, one of class 2, two of class 7 and one of class 6. This is a **corpus cross-check**, not a causal test; shipped runtime OBJ/ODEF does not preserve the editor's editable rectangular dimension strings or list order. No original editable `.I76` workspace or version-proven export matching a shipped mission was available.

## Remaining gaps

1. An original `.I76` authoring workspace would permit direct extraction of class 0x50..0x53 dimensions, exact insertion order, and a controlled before/after terrain export; no byte-identical roundtrip has been established.
2. Need original-code execution or controlled editor run to fix x87 rotate/quantization details, sentinel edge cases and numeric four-pass smoothing bit-for-bit.
3. Whether runtime intersection GEO faces participate in independent rigid-body collision remains a separate research question (`i76.exe` scene list `00644200` / insertion `004925F0` versus wheel terrain probe `00440740`).
4. Source-file adjacency is provisional: object authoring/loading functions near `00409840`–`0040AC20`, terrain surface helpers near `0041F150`–`0041F4A0`, road/smoothing code near `00421BE0`–`00422C1D`; no original source filenames or translation unit boundaries are recovered.

## Reproduction and validation

The scripts `verify_original_editor_functions.py` and `v23_overlap_semantic_model.py` respectively check fixed native opcode anchors in the **private original PE** and exercise a minimal analytical model of the recovered branch order. On this environment: **43/43** native opcode/jump-table assertions passed; **7/7** analytical scenarios passed. Original editor MD5 matches, and the independently read-only decompiled annotated program reports the same MD5. Neither script executes the original editor GUI nor proves all uninspected codepaths.
